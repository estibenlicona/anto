## 3. Verificación automatizada y excepciones

- [x] 3.1 Agregar `tsx` a las devDependencies de la raíz (hoy solo está dentro de los paquetes) para poder correr el script de auditoría desde el monorepo.
- [x] 3.2 Escribir `scripts/security-audit.ts`: corre `pnpm audit --prod --json` y `pnpm audit --json`, aplica los umbrales moderate y high respectivamente, informa severidad, paquete, título, versión que corrige y advisory, y sale con código distinto de cero si algo queda sin cubrir. Se parsea el JSON en vez de usar `--audit-level` porque hace falta el `github_advisory_id` de cada hallazgo para poder casar excepciones por advisory (tarea 3.5).
- [x] 3.3 Definir el formato de `security-exceptions.json` — paquete, advisory, motivo, responsable y fecha de revisión — y hacer que el script rechace toda excepción a la que le falte cualquiera de esos campos.
- [x] 3.4 Implementar en el script el vencimiento: una excepción cuya fecha de revisión ya pasó vuelve a hacer fallar la verificación, evaluando contra la fecha de la corrida.
- [x] 3.5 Implementar que las excepciones se apliquen por advisory concreto: una vulnerabilidad por encima del umbral que no coincida con ninguna excepción registrada hace fallar igual, sin que las existentes la cubran por acumulación. El script además marca la excepción que ya no casa con ningún hallazgo, para que no quede acumulando.
- [x] 3.6 Hacer que el script informe siempre qué excepciones están vigentes y hasta cuándo, incluso cuando la verificación pasa — una excepción que nadie ve es una excepción olvidada.
- [x] 3.7 Declarar la tarea de raíz `//#security:audit` en `turbo.json` con `cache: false`, y hacer que `test` dependa de ella. Nota de implementación: el subproceso se lanza con `execSync` y un comando literal, no con `execFileSync` + array. En Windows `pnpm` es un `.cmd` que Node 24 se niega a spawnear sin shell (`EINVAL`), y pasar un array *con* shell dispara `DEP0190` porque el shell concatena argv en vez de escaparlo — un gate de seguridad que dispara una deprecación de seguridad no es el ejemplo a dejar.
- [x] 3.8 Verificar el enganche corriendo `pnpm test` **sin** invocar la auditoría a mano y confirmar que igual corrió. Turbo la reporta como `//:security:audit: cache bypass, force executing`.
- [x] 3.9 Verificar que una segunda corrida seguida de `pnpm test` vuelve a ejecutar la auditoría en vez de servirla desde el caché de Turbo. Confirmado: en la segunda corrida los builds salieron por `cache hit, replaying logs` mientras la auditoría volvió a ejecutarse.
- [x] 3.10 Escribir `.github/workflows/ci.yml` con lint, test, build y la auditoría, más un disparo programado que cubra la verificación periódica. Dejar anotado en el propio workflow que queda latente hasta que el proyecto tenga remoto.

## 4. Vulnerabilidades: resolver lo que se puede, registrar lo que no

- [x] 4.1 Actualizar `tsup` (y con ella `esbuild`) en `packages/cli` y `packages/tokens`. **Sin acción posible:** `tsup` ya está en su última versión publicada (8.5.1), que sigue trayendo `esbuild` 0.27.7. Además los dos hallazgos de `esbuild` son `low` y `moderate` en la cadena de build, así que no cruzan ninguno de los dos umbrales y no bloquean. Forzar `esbuild >=0.28.1` por override bajo `tsup` sería asumir riesgo de romper el build sin ganancia para el gate; se deja como está y se anota.
- [x] 4.1b **No previsto en el plan:** el gate reveló una cuarta vulnerabilidad de runtime que la investigación por severidad no había separado — `prismjs` (GHSA-x7hr-w5r2-h6wg, moderate), que llega al sitio por `react-syntax-highlighter > refractor`, el cual fija `~1.27.0`. La versión parcheada (`>=1.30.0`) es un release de parche, así que se resolvió con un override de pnpm en vez de una excepción o de un salto mayor de `react-syntax-highlighter`. Verificado: `refractor` ahora resuelve a 1.30.0 y `apps/docs` sigue construyendo. El override va en `package.json` bajo `pnpm.overrides` — en `pnpm-workspace.yaml` se ignora silenciosamente con pnpm 9, que fue el primer intento y no tuvo efecto.
- [x] 4.2 Registrar en `security-exceptions.json` la excepción de `vite` (GHSA-fx2h-pf6j-xcff, la única alta) con motivo — el parche solo existe en la línea 6.x, migración mayor — y fecha de revisión.
- [x] 4.3 Registrar la excepción de `react-router` con el mismo criterio. Resultaron **tres** advisories distintos, no uno: `GHSA-337j-9hxr-rhxg`, `GHSA-wrjc-x8rr-h8h6` y `GHSA-jjmj-jmhj-qwj2`.
