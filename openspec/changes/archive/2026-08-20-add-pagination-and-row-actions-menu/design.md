## Context

Ver proposal.md — Why. Lo que condiciona el cómo:

- **Ningún endpoint del backend pagina hoy** (`grep` de `PageSize`/`PageNumber`/`Skip(`/`Take(` en todo `backend/src` no encuentra nada) — esta es la primera paginación de todo el catálogo, así que este change fija la convención en vez de seguir una ya existente.
- `IRepository<T>.GetAllAsync(CancellationToken)` es la interfaz genérica compartida por **todos** los repositorios (`Domain/Interfaces/IRepository.cs`), no sólo por Person/Squad/Allocation. Cambiar su firma rompería a cualquier otro consumidor (Company, BauTask, Initiative, etc.) fuera del alcance de este change — por eso cada repositorio afectado gana un método nuevo, propio de su interfaz específica, en vez de tocar la interfaz genérica.
- `PeopleEndpoints.GetAllAsync` → `GetPeopleUseCase.ExecuteAsync(ct)` → `IPersonRepository.GetAllAsync(ct)` (heredado de `IRepository<T>`) → `DbSet.AsNoTracking().ToListAsync(ct)`. Mismo patrón, sin `Where`, en `SquadsEndpoints`/`GetSquadsUseCase`/`ISquadRepository`.
- `AllocationsEndpoints.GetBySquadAsync` es distinto: `GetAllocationsBySquadUseCase` trae **todas** las asignaciones de la célula (`IAllocationRepository.GetBySquadAsync`, un simple `Where(a => a.SquadId == squadId)`), y **después**, en memoria, resuelve nombre de persona y de célula con `Task.WhenAll` sobre `GetByIdAsync` (N+1 por asignación) y ordena por `personMap.GetValueOrDefault(a.PersonId)` — porque `Allocation` no guarda el nombre de la persona, sólo su id. Ese orden por nombre es exactamente el que hoy ve el usuario en la lista, así que la versión paginada tiene que preservarlo sin volver a traer todas las asignaciones a memoria primero (eso anularía el propósito de paginar).
- Frontend: `personService.list()`/equivalentes en squads/allocations devuelven hoy `Promise<Dto[]>` (array plano); `usePeople`/`useSquads`/hook de allocations guardan ese array en un solo `useState` y lo pasan tal cual a `PersonAdapter.toEntity` por ítem. `PeopleList`/`SquadsList`/`AllocationsList` reciben la lista completa ya mapeada, sin ningún control de paginación.
- `PaginationBar` (`@tuya-ui/components`) ya expone `page`, `pageCount`, `onPageChange`, `total`, `pageSize`, `pageSizeOptions`, `onPageSizeChange` — encaja directo con un sobre `{ items, page, pageSize, totalCount, totalPages }`.
- `Menu`/`MenuItem` (`@tuya-ui/components`) ya resuelven trigger + popover accesible + ítem destructivo (`destructive` prop, colorea con el rol `danger`) — no hace falta ningún primitivo nuevo en tuip.

## Goals / Non-Goals

**Goals:**
- Paginación real (a nivel de base de datos, no recortada en memoria después de traer todo) en los tres endpoints de listado.
- Una única forma de sobre paginado, reutilizada por los tres endpoints y sus tres mocks — no tres formas distintas.
- El menú de acciones reemplaza los botones sueltos con el mínimo cambio de comportamiento: mismas dos acciones, mismos handlers `onEdit`/`onDelete`/`onRemove` que ya reciben `PeopleList`/`SquadsList`/`AllocationsList`.

**Non-Goals:**
- No se pagina `GET /people/{id}/allocations` (por persona) — no tiene consumidor hoy, ver proposal.md.
- No se agrega ordenamiento configurable por el usuario (sort) — el orden por defecto de cada lista (nombre) no cambia, sólo se pagina sobre ese mismo orden.
- No se toca `IRepository<T>` ni ningún otro repositorio que no sea Person/Squad/Allocation.

## Decisions

- **`PagedResult<T>` como sobre único y compartido**, en `Application/DataTransferObjects/PagedResult.cs`: `record PagedResult<T>(IReadOnlyList<T> Items, int Page, int PageSize, int TotalCount, int TotalPages)`, con `TotalPages = (int)Math.Ceiling(TotalCount / (double)PageSize)`. Los tres endpoints devuelven `PagedResult<PersonDto>`/`SquadDto`/`AllocationDto` — mismo nombre de campos en los tres, para que el cliente HTTP los trate igual.
- **`page`/`pageSize` como query params, no como parte del path ni del body**: `GET /people?page=1&pageSize=10`. Es el único punto de entrada de un `GET` de listado, y sigue el estándar REST más común — no hay convención previa en este backend que seguir en su lugar.
- **Valores por defecto y límites se clampan en el propio endpoint, sin un validador nuevo**: `page < 1` → `1`; `pageSize < 1` → `1`; `pageSize > 100` → `100`; sin `page`/`pageSize` en la URL → `page=1`, `pageSize=10`. No se agrega un `Validator` de FluentValidation nuevo (el patrón que ya usan `Create*Validator`) porque no hay nada que rechazar con un error 400 — un `page`/`pageSize` fuera de rango tiene una respuesta razonable (la página 1, o el tope de 100) en vez de un error, así que clamplear alcanza y mantiene el alcance acotado a lo pedido.
- **Cada repositorio afectado gana un método propio, no se toca `IRepository<T>.GetAllAsync`.** `IPersonRepository.GetPagedAsync(int page, int pageSize, CancellationToken)` y `ISquadRepository.GetPagedAsync(...)` devuelven `(IReadOnlyList<T> Items, int TotalCount)` — un conteo (`CountAsync`) más una página (`OrderBy(x => x.Name).Skip((page-1)*pageSize).Take(pageSize)`), ambos ejecutados por EF Core como SQL, no en memoria.
- **`IAllocationRepository.GetBySquadPagedAsync(Guid squadId, int page, int pageSize, CancellationToken)` reemplaza el patrón N+1 del use case por una sola consulta con `Join` a `People`, ordenada por el nombre de la persona.** Hoy `GetAllocationsBySquadUseCase` trae todas las asignaciones de la célula y después resuelve nombres con `Task.WhenAll(GetByIdAsync)` uno por uno — funciona porque nunca pagina, así que "todas" es manejable. Para paginar de verdad (`Skip`/`Take` a nivel de base de datos) el orden por nombre tiene que resolverse **dentro** de la misma consulta, no después: el repositorio hace `DbContext.Allocations.Where(a => a.SquadId == squadId).Join(DbContext.People, a => a.PersonId, p => p.Id, (a, p) => new { Allocation = a, PersonName = p.Name }).OrderBy(x => x.PersonName).Skip(...).Take(...)`, y el use case arma los DTOs a partir de ese resultado ya trae el nombre de persona incluido — sin el `Task.WhenAll` de hoy. El nombre de célula (siempre el mismo para las N asignaciones de una página) se resuelve con un único `GetByIdAsync(squadId)`, no por asignación.
- **Los tres mocks leen `page`/`pageSize` de `request.url`'s `searchParams`, con los mismos defaults y límites que el backend real**, y devuelven el mismo `PagedResult`-shape a mano (los handlers ya son TypeScript plano, sin acceso al tipo compartido del backend — se define un tipo `PagedResult<T>` equivalente en el frontend, en `shared/services/` o junto a cada servicio, para que TypeScript infiera la forma en el cliente).
- **`PeopleList`/`SquadsList`/`AllocationsList` reciben `page`, `pageCount`, `total`, `pageSize`, `onPageChange`, `onPageSizeChange` como props nuevas**, agregadas por sus hooks (`usePeople`/`useSquads`/hook de allocations), que pasan a guardar `page`/`pageSize` en `useState` (tamaño inicial 10) y a re-pedir cuando cualquiera de los dos cambia — mismo patrón que ya usa el ejemplo "Integración completa" de `PaginationBar` en la documentación de tuip.
- **El menú de acciones no introduce estado propio**: cada fila arma su propio `<Menu trigger={...}><MenuItem onSelect={() => onEdit(row)}>Editar</MenuItem><MenuSeparator/><MenuItem destructive onSelect={() => onDelete(row)}>Eliminar</MenuItem></Menu>` — Radix (que usa `Menu` por dentro) ya maneja que sólo uno esté abierto a la vez sin coordinación explícita.

## Risks / Trade-offs

- [Cambiar la forma de respuesta de tres endpoints reales es breaking] → Documentado como tal en proposal.md; dentro de este monorepo sólo el propio frontend de este change los consume (ver proposal.md — Impact), así que el breaking change se resuelve en el mismo change, sin dejar un consumidor roto.
- [El join a `People` para ordenar las asignaciones por nombre acopla `AllocationRepository` a la tabla `People`, algo que `GetBySquadAsync` (sin paginar) no necesita hoy] → Es el mismo acoplamiento que ya tiene el use case hoy (llama a `IPersonRepository.GetByIdAsync` para lo mismo) — sólo se mueve de la capa de aplicación a la de infraestructura, donde EF Core lo puede resolver en una sola consulta en vez de N+1.
- [Clamplear en silencio `page`/`pageSize` fuera de rango, en vez de devolver 400] → Es una elección deliberada de scope (ver Decisions) — un cliente que pide `pageSize=9999` obtiene 100 resultados en vez de un error, lo cual es razonable para un parámetro de paginación y evita introducir un validador nuevo sólo para esto.
- [Los tres mocks reimplementan a mano la misma lógica de recorte que hace el backend real (`Skip`/`Take` sobre el array en memoria)] → Ya es el patrón establecido de este proyecto (cada handler de mock reimplementa su propia validación, ver `isValidCreateRequest` en `people.handlers.ts`) — no hay un mecanismo compartido entre backend y mocks hoy, y agregar uno está fuera del alcance de este change.

## Notas de implementación

- **El backend real no se pudo verificar de punta a punta contra una base de datos — hallazgo preexistente, no de este change.** El repo no tiene ninguna migración de EF Core ni mecanismo de seed; `GET /api/v1/people` contra una LocalDB recién creada falla en el login (`Cannot open database`), antes de llegar a ejecutar la consulta. La paginación se verificó igual por dos vías indirectas pero sólidas: 15 tests de use case con repositorios mockeados (`GetPagedAsync`/`GetBySquadPagedAsync` devuelven exactamente lo que el mock configura) y verificación visual completa contra los mocks de MSW, que replican la misma forma de respuesta. Provisionar una base de datos real es un problema separado, anterior a este change.

- **`AllocationsContainer` reutiliza `usePeople()`/`useSquads()` para poblar selectores, no para una lista paginada propia.** No estaba anticipado en el diseño original: al paginar esos hooks con `pageSize=10` por defecto, el selector de célula y el de persona del formulario de asignación habrían mostrado sólo los primeros 10 registros. Se resolvió agregando un parámetro opcional `initialPageSize` a `usePeople`/`useSquads` (default 10, así que `PeopleContainer`/`SquadsContainer` no cambian), y `AllocationsContainer` pasa `100` explícitamente — suficiente para los datos de ejemplo de este proyecto, documentado como tal en el propio código en vez de silencioso.

## Migration Plan

Sin datos que migrar (no hay una tabla de "estado de paginación" ni nada persistido que cambie de forma) — el único cambio de contrato es la respuesta HTTP de tres endpoints `GET`, cubierto como breaking en proposal.md. Se implementa primero el backend (y sus tests), después los mocks, y por último el frontend — así cada capa se verifica contra una forma ya estable, en vez de against un contrato que todavía se está definiendo.
